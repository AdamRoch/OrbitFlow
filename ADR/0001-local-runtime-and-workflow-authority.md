# Local workflow authority and isolated browser applications

Status: Accepted implementation decision under Adam's delegated design authority, 2026-09-06. Pinned runtime startup, native file tools, structured results and usage have been exercised through real provider turns.

Use TypeScript for the React UI and Node server, and PostgreSQL for configurations, immutable run snapshots, addressed messages, approvals, revisions and events. The run detail exposes its frozen agents and graph so execution history remains understandable after configuration changes. A single local executor claims queued work; runtime sessions execute one agent turn and never own the graph. Persist each handoff with the state transition in one transaction. Interrupted external turns fail closed rather than silently spend again.

Each workflow node declares its accepted terminal outcomes. The engine resolves a structured result through an exact edge, an explicit terminal outcome, then a wildcard edge. An unmatched outcome fails with an actionable error and retains its message and artifact revision. This prevents an agent from silently skipping review by returning a plausible but unconfigured outcome.

Use pinned OpenCode for native file tools and structured results inside a fresh constrained container per turn. Limit the initial product to static browser applications. No generated shell or server code executes on the host. Generated previews run on a separate loopback origin per application lineage (`app-<root-run-id>.localhost`) with a restrictive content security policy; the orchestration API rejects cross-origin mutations. The runtime receives only its explicitly configured provider credential, no host home, application database credentials, Docker socket, or old project data. Source revisions are retained in PostgreSQL and can be inspected before release.

One PostgreSQL container plus the local application process and ephemeral runtime containers keeps the local setup small. This is a single-user local product, not a claim of production multi-tenancy or distributed execution. Token and cost data come from the real runtime; unknown or historically incomplete usage is labeled rather than replaced with zero. Before a turn, the engine calculates the smaller remaining platform and agent allowance. The runtime watches OpenCode's reported cost and cancels when observed usage reaches it. Reporting delay and work already in flight can cross that threshold, so a provider-side spending cap remains the hard monetary boundary. Unknown cost blocks later paid turns pending reconciliation.

Two templates use the same configurable graph and agent settings as user-created workflows. Approval is tied to the pending turn or exact artifact revision with a unique decision token, compared under the run row lock. Old browser actions and Telegram commands cannot approve a newer unseen result. Configuration writes are serialized within the sole local app process to preserve channel uniqueness and graph references.

A schedule may target only a workflow containing the scheduled agent. Its next wake and pending dispatch survive restart, and durable request messages name `schedule:<agentId>` as the sender. Telegram is a separately configured bot and allowlisted chat; the existing application's bot is untouched. Inbound updates use durable idempotency keys. Polling and run monitoring share one in-process outbox drain so they cannot concurrently send the same row. Telegram offers no send idempotency key, so a crash after Telegram accepts a reply but before OrbitFlow records the receipt can still duplicate one reply.

Recovery resumes an inactive failed run at its retained node using the original snapshot and source, rather than replaying completed turns. Unknown cost must first be reconciled with a durable receipt and explanation; missing historical token counts remain explicitly unavailable. OpenCode 1.18.29 rejects structured assistant records through its history decoder, so complete SSE assistant snapshots after the exact session idle event are the primary usage record. Workflow-turn guardrails stay in the graph engine; they are not mapped to OpenCode native tool-cycle limits, whose final-cycle assistant prefill is incompatible with Claude 4.6.

The local demonstration's Reviewer model is now `openrouter/openai/gpt-5.4`, while Builder remains the configured Claude Sonnet 4.6. Sonnet repeatedly exhausted review allowances despite scoped procedures; the alternative is a configurable agent setting, not a second runtime or a hardcoded review path. GPT-5.4 supports function calling and structured outputs in the [official model documentation](https://developers.openai.com/api/docs/models/gpt-5.4), and the live OpenRouter model catalog exposes the selected ID. Actual execution evidence, rather than model reputation, determines whether this choice succeeds. Historical run models and settings remain immutable.
